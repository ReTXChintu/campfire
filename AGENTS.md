# Campfire — monorepo

`apps/frontend` (Vite + React SPA) and `apps/backend` (Express + TypeScript, compiled to `dist/` and run with plain `node`, no framework magic) are npm workspaces. `apps/mobile` (Flutter — Android and Windows desktop; iOS/web platform folders exist but aren't actively targeted) is a separate app in the same monorepo but is **not** an npm workspace (Flutter has its own toolchain/`pubspec.yaml`). Admin/curation screens exist in two places now: the web app (unconditional) and `apps/mobile`'s Windows build only (`lib/screens/admin/`, gated behind `platform_info.dart`'s `isDesktopAdminCapable` — both a router redirect in `app_router.dart` and the top-bar menu entry check it, on top of every `/api/admin/*` call still being independently enforced server-side via `requireAdmin`). The Android build never shows admin UI, by design, same as before.

- Root scripts (`npm run dev` / `build` / `lint`) fan out to the two npm workspaces — see root `package.json`. Mobile has its own `flutter` commands (see `apps/mobile/README.md`), plus `npm run mobile:analyze` / `mobile:build:web` convenience wrappers.
- `release-it` runs from the repo root only; it bumps root + both `apps/*/package.json` (via `npm version --workspaces`) *and* `apps/mobile/pubspec.yaml` (via `scripts/sync-mobile-version.mjs`, since that's not an npm package) together in one commit/tag (see `.release-it.json`'s `after:bump` hook).
- **No OAuth** — plain email/password (bcrypt). One admin account is seeded into Mongo from `ADMIN_EMAIL`/`ADMIN_PASSWORD` (`apps/backend/.env`) on every startup (`lib/users.ts`'s `seedAdminUser`, called from `index.ts`); everyone else signs up via `POST /auth/signup` (`lib/users.ts`'s `createUser`, open — no invite code), which never grants admin (`isAdminEmail()` only ever matches the one seeded email). `POST /auth/login` and `/auth/signup` are the only ways in, on web and mobile alike. Auth is a self-issued JWT, sent as `Authorization: Bearer` — not cookies, since frontend/backend/mobile are all cross-origin from the backend in production. Web `<video>`/`<img>` tags that can't set that header use a separately-scoped, short-lived media token instead (`GET /api/media-token`; see `apps/backend/src/middleware/mediaAuth.ts`). Mobile uses the same media token for video/subtitle streams (Flutter Web's `<video>` has the identical header limitation as a browser; native Android/iOS *can* set headers but the token path is used everywhere for one consistent code path) but plain Bearer headers for images (`Image.network` supports custom headers on every Flutter platform, unlike `<img>`).
- The backend is the only thing that touches `ffmpeg`/Google Drive; it needs a persistent process (VPS), not a serverless function — that's the whole reason this was split out of the previous single Next.js app.
- Video playback has three `seekMode`s (`GET /api/video/:fileId`, computed in `routes/catalog.ts` from the Drive mimeType): `"native"` (mp4/webm/ogg — real Range seeking), `"restart"` (anything else *except* MKV — live ffmpeg remux to fragmented MP4 on every seek, no real duration/Range of its own) and `"raw"` (MKV specifically). Only `"native"` plays on web — for anything else `WatchPage.tsx` shows `DesktopAppRequiredNotice` (a "get the app" link) instead of mounting `VideoPlayer` (`VideoPlayer.tsx` still carries its older restart-mode branches, but they're no longer reachable from `WatchPage`). `apps/mobile` has a single player widget on every platform: `MediaKitVideoPlayer` (libmpv via `media_kit`/`media_kit_video`), mounted by `watch_screen.dart` — it decodes any container, exposes embedded audio/subtitle tracks, and demuxes/seeks MKV/native content for real; for `"restart"` content it falls back to a reopen-at-a-new-`t=`-offset trick, since that stream still isn't truly seekable. (A second `video_player`-based engine used to handle native mp4 on Android; it was dropped — no audio-track picker, and no Windows implementation.) MKV specifically requests `GET /api/stream/:fileId?raw=1`, which opts into a raw Drive byte passthrough (`isNativelyPlayable(mimeType) || (isMkv(mimeType) && wantsRaw)` in `routes/stream.ts`) instead of the ffmpeg remux — but only on that explicit `raw=1` request; an MKV `/api/stream` request *without* it (e.g. the web admin curation page's plain `<video controls>` preview, which needs to keep working for any format) still gets the remuxed MP4, unchanged.
- **Everything is plain HTTP, always** — no TLS anywhere in this repo (backend, frontend's `serve.mjs`, and every client). If you need HTTPS in production, put a reverse proxy in front and point each app's `*_URL`/`API_URL` config at that; nothing in the apps themselves needs to change either way.
- Deployment can also be pm2 on a single VPS over `http://<IP>:<PORT>` (no domain/reverse proxy) — root `ecosystem.config.js` reads the root `.env` (just ports; separate from each app's own `.env`) and starts both apps. See the root README's "Deployment" section.
