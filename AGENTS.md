# Campfire — monorepo

`apps/frontend` (Vite + React SPA) and `apps/backend` (Express + TypeScript, compiled to `dist/` and run with plain `node`, no framework magic) are npm workspaces. `apps/mobile` (Flutter — Android and Windows desktop; iOS/web platform folders exist but aren't actively targeted) is a separate app in the same monorepo but is **not** an npm workspace (Flutter has its own toolchain/`pubspec.yaml`). Admin/curation screens exist in two places now: the web app (unconditional) and `apps/mobile`'s Windows build only (`lib/screens/admin/`, gated behind `platform_info.dart`'s `isDesktopAdminCapable` — both a router redirect in `app_router.dart` and the top-bar menu entry check it, on top of every `/api/admin/*` call still being independently enforced server-side via `requireAdmin`). The Android build never shows admin UI, by design, same as before.

- Root scripts (`npm run dev` / `build` / `lint`) fan out to the two npm workspaces — see root `package.json`. Mobile has its own `flutter` commands (see `apps/mobile/README.md`), plus `npm run mobile:analyze` / `mobile:build:web` convenience wrappers.
- `release-it` runs from the repo root only; it bumps root + both `apps/*/package.json` (via `npm version --workspaces`) *and* `apps/mobile/pubspec.yaml` (via `scripts/sync-mobile-version.mjs`, since that's not an npm package) together in one commit/tag (see `.release-it.json`'s `after:bump` hook).
- **No OAuth** — plain email/password (bcrypt). One admin account is seeded into Mongo from `ADMIN_EMAIL`/`ADMIN_PASSWORD` (`apps/backend/.env`) on every startup (`lib/users.ts`'s `seedAdminUser`, called from `index.ts`); everyone else signs up via `POST /auth/signup` (`lib/users.ts`'s `createUser`, open — no invite code), which never grants admin (`isAdminEmail()` only ever matches the one seeded email). `POST /auth/login` and `/auth/signup` are the only ways in, on web and mobile alike. `POST /auth/reset-password` takes just an email and a new password, so it refuses the admin account (with the same answer as an unknown email); that password only comes from `.env`. Auth is a self-issued JWT, sent as `Authorization: Bearer` — not cookies, since frontend/backend/mobile are all cross-origin from the backend in production. Web `<video>`/`<img>` tags that can't set that header use a separately-scoped, short-lived media token instead (`GET /api/media-token`; see `apps/backend/src/middleware/mediaAuth.ts`). Mobile uses the same media token for video/subtitle streams (Flutter Web's `<video>` has the identical header limitation as a browser; native Android/iOS *can* set headers but the token path is used everywhere for one consistent code path) but plain Bearer headers for images (`Image.network` supports custom headers on every Flutter platform, unlike `<img>`).
- The backend is the only thing that touches `ffmpeg`/Google Drive; it needs a persistent process (VPS), not a serverless function — that's the whole reason this was split out of the previous single Next.js app.
- Video playback has three `seekMode`s (`GET /api/video/:fileId`, computed in `routes/catalog.ts` from the Drive mimeType): `"native"` (mp4/webm/ogg — real Range seeking), `"restart"` (anything else *except* MKV — live ffmpeg remux to fragmented MP4 on every seek, no real duration/Range of its own) and `"raw"` (MKV specifically). Only `"native"` plays on web — for anything else `WatchPage.tsx` shows `DesktopAppRequiredNotice` (a "get the app" link) instead of mounting `VideoPlayer` (`VideoPlayer.tsx` still carries its older restart-mode branches, but they're no longer reachable from `WatchPage`). `apps/mobile` has a single player widget on every platform: `MediaKitVideoPlayer` (libmpv via `media_kit`/`media_kit_video`), mounted by `watch_screen.dart` — it decodes any container, exposes embedded audio/subtitle tracks, and demuxes/seeks MKV/native content for real; for `"restart"` content it falls back to a reopen-at-a-new-`t=`-offset trick, since that stream still isn't truly seekable. (A second `video_player`-based engine used to handle native mp4 on Android; it was dropped — no audio-track picker, and no Windows implementation.) MKV specifically requests `GET /api/stream/:fileId?raw=1`, which opts into a raw Drive byte passthrough (`isNativelyPlayable(mimeType) || (isMkv(mimeType) && wantsRaw)` in `routes/stream.ts`) instead of the ffmpeg remux — but only on that explicit `raw=1` request; an MKV `/api/stream` request *without* it (e.g. the web admin curation page's plain `<video controls>` preview, which needs to keep working for any format) still gets the remuxed MP4, unchanged.
- **Movie/series requests** (`lib/mediaRequests.ts`, `routes/requests.ts`, `routes/admin/requests.ts`) let any signed-in viewer ask for something that isn't in the library. A request is deliberately only a **title plus one reference** — either an IMDb/TMDb link or an uploaded image (`lib/requestImages.ts`, 5MB cap, stored under `REQUEST_IMAGES_DIR` like renditions, served from `GET /api/request-image/:id` with plain Bearer auth). Movie-vs-series and year are never asked of the requester: they come from the TMDb lookup when `TMDB_API_KEY` is set (`lib/referenceLink.ts` — entirely optional, a failed/absent lookup just means no preview card) and are otherwise the admin's to set. The board is visible to everyone, which is what makes the "N people want this" upvote dedupe work. Two transitions are enforced server-side, not just in the UI, since three clients hit the same endpoints: declining requires an `adminNote` (the requester reads it) and marking one `added` requires a `catalogRef` to the item that fulfilled it. With `TMDB_API_KEY` set, the form (web `RequestModal.tsx`, mobile `request_sheet.dart`) leads with a title search, `GET /api/requests/tmdb-search` (`lib/tmdbSearch.ts`): picking a result just fills in the same title + TMDb link a paste would, and each result says whether it's already published (`inLibrary`, matched on catalog `artwork.tmdbType/tmdbId`) or already openly requested (`existingRequest`, matched on `refMeta` or an unresolved TMDb `refLink` — offered as an upvote instead of a duplicate). Without the key it answers `available: false` and both clients show the old link/image form alone, which otherwise stays as the "Can't find it?" fallback. The admin queue is web + Windows only, same rule as every other `/api/admin/*` screen.
- **Catalog artwork and metadata** (`lib/artwork.ts`, `lib/episodeArtwork.ts`, `lib/catalogMeta.ts`, `routes/admin/artwork.ts`): top-level movies (root videos) and series (root folders) are matched to TMDb, automatically from the title/filename after each scan and once at startup (exact-name match only, year within ±1), or from an IMDb/TMDb link pasted in admin. Each match then makes one detail call (`append_to_response`) for the tagline, runtime, genres, certificate (India first, then US/GB), TMDb score, season/episode counts, billed cast and the image lists — from which it picks a *textless* backdrop (the spotlight writes its own title over it), an English poster, and a PNG wordmark. Only ids, paths and facts are stored, on the catalog doc (`artwork`, `artworkAutoOff`, `artworkTriedFor`); images are downloaded on first view into `ARTWORK_DIR` (server disk, not Drive, because the service account has no storage quota) and served through the existing `/api/thumbnail/:fileId` and `/api/thumbnail-folder/:folderId` routes. TMDb artwork wins over a Drive `thumbnail.*`, which is only the fallback. `?shape=poster` returns the 2:3 poster (web's poster cards ask for it), `?shape=logo` the wordmark (404 when there is none — clients fall back to text); the default is the 16:9 backdrop. Cast headshots come from `/api/cast-image/:kind/:id/:index`, addressed by position in the stored cast so no client ever supplies a TMDb path. Listings report a folder with artwork but no Drive image as `thumbnailFileId: "tmdb"`, because every client only null-checks that field, which is what lets already-installed builds show artwork. A match also replaces a raw filename with TMDb's title, but only when the two are the same title bar formatting or release noise (`cleanedTitle`) and never when an admin typed it — for the rest there are explicit `use-tmdb-title(s)` endpoints, which do overwrite a hand-typed name because an admin asked. **Episodes** (`lib/episodeArtwork.ts`) get their real name, synopsis, still, air date and score. Each file's episode comes from its own *Drive* name first (`parseEpisodeNumber`: `S01E04`, `AOT S1 - 04`, `1x04`, `Episode 4`… — never the curated title, since publish-rule patterns can be wrong), with unreadable names filling the leftover numbers only on an exact fit, and position within the season as the last resort. A *bonus* file (`S02.Bonus.E03`) is never a regular episode: it's matched to TMDb's Specials (season 0) by name — same bonus number, same season (`matchSpecial`) — since TMDb numbers specials in one running list. A file a run can positively say has no match loses any TMDb data an earlier pass gave it. `episodeOrder` is a sort position, never read as an episode number: files that name their own episode set it outright (repairing a wrong positional order), a position-matched folder with only some orders set is frozen whole so renames can't reshuffle it, and an order every file already has is an admin's and is left alone. Which season a folder holds is guessed from its name *and Drive name* (`guessSeasonNumber`, since matching rewrites the title) and overridable per folder via `tmdbSeason`; `episodeArtworkOff` turns a series' episode naming off. Viewer-facing responses flatten all of this through `titleMeta`/`episodeMeta`, keeping the old `year`/`overview` field names so older clients are unaffected. Needs `TMDB_API_KEY`; `scripts/smoke-artwork.mjs` tests it end to end against a mock TMDb (224 checks). `POST …/folder/:id/publish-episodes` publishes a series' never-curated, TMDb-named episodes: always previewed first (anything but an explicit `dryRun: false` only previews), touching only *pending* episodes (a curated-but-unpublished one was held back on purpose), and flagging any season matched by position. Library list items also carry each title's `genres` and first six `castNames`, which is what search (title, genre or actor), Discover's genre chips and rating sort, and Home's genre rows all run on client-side — `apps/frontend/src/lib/discovery.ts` and `apps/mobile/lib/models/discovery.dart` hold that logic and must stay in step.
- **`GET /api/library` returns `spotlight`**, an ordered carousel of up to six slides that interleaves recently curated titles with fulfilled requests (`kind: "new" | "featured" | "request"`), so a request landing in the library is impossible to miss. `spotlight[0]` is always a library pick. The older single `hero` field is still sent unchanged so an already-installed Android/Windows build keeps rendering against a newer backend — remove it once those are gone.
- **Up next and autoplay** (`lib/upNext.ts`; `apps/mobile/lib/widgets/up_next.dart`, `apps/frontend/src/components/UpNext.tsx` + `lib/upNext.ts`): `GET /api/video/:fileId` adds `upNext` — the next episode, crossing into the next season (seasons ordered by number, specials and unnumbered folders last), else after a film or a finale the library's best match — and `suggestions` (up to six: 3 points per shared genre, 2 per shared lead actor, plus TMDb score; films the viewer finished are left out). `nextFileId` crosses seasons too, so an installed app carries on. The players show a card at `outroStart` (else 25 s from the end) that counts down (10 s for an episode, 15 s for a suggestion) and plays it; after two in a row with no input at all the next one waits on "Still watching?" (a module/top-level counter, reset by any input). Dismissing it ends the title on an end screen with more like this. In a party, followers never autoplay and the web keeps its plain next-episode hop. The autoplay switch is per device.
- **Audio and subtitle tracks** (`lib/mediaTracks.ts`, `routes/admin/tracks.ts`; `scripts/smoke-tracks.mjs` checks it end to end on real Drive files):
  - **Reading.** Every file's embedded tracks are read once with ffprobe (`probeFileTracks`) and stored on its catalog doc as `tracks`. Reads run in the background, two at a time, at startup and after each scan. A file is read again when its Drive size changes, or a day after a failed read. Tracks are numbered per kind from 1 in file order (`n`), image subtitles included, because that is mpv's aid/sid numbering in the apps: `n` is how a name set in admin is found again in the player.
  - **Naming.** Admins name tracks and pick a default audio/subtitle (`trackNaming`) on a series, a season or a single video; the nearest one wins per field. A folder's names are stamped on save with the language each position held in the usual layout (`match`), and `fitNaming` leaves them off any episode laid out differently.
  - **Consistency report.** `trackReport` groups a series' episodes by their languages in order and words what the odd ones lack or add, so the admin can replace those files.
  - **Viewer fields.** `GET /api/video/:fileId` adds `audioTracks`/`subtitleTracks` (named) and `startAudio`/`startSubtitle`. `startTracks` picks them, first match wins: this video's saved pick, the latest pick anywhere in the series (`getSeriesPreferences`, by language, since release titles differ per episode), the viewer's profile languages (`PUT /auth/me/languages`, with subtitles off / always / only when the audio isn't theirs), then the admin's default. The old `initial*` fields stay for installed apps. `languages` on `/api/video` and `/api/folder` lists what a title has, marking languages only some episodes have.
  - **Language codes.** All of them go through `canonicalLanguage`/`fileLanguage` in `lib/languageNames.ts`: "en"/"eng" are one language, and an untagged track titled "Hindi DD5.1" counts as Hindi.
- **Seek-bar previews** (`lib/trickplay.ts`, `routes/trickplay.ts`): `GET /api/trickplay/:fileId` returns the manifest (200) or queues it (202) on a video's first play. One video at a time, one sequential read from Drive with only keyframes decoded, a frame every 10 s (`fps … :round=up`, so frame *i* is second 10·*i* or the keyframe just before), tiled locally into 10×10 sheets of 192×108, kept in `TRICKPLAY_DIR`, a failure remembered for a week. `TRICKPLAY=off` stops new ones (each costs a full download of the file). Sheets are at `…/sheet/:n`, Bearer or media token (web draws them as CSS backgrounds). `scripts/smoke-trickplay.mjs` checks it on synthetic local videos — no Drive or Mongo needed.
- **Explore** (`lib/explore.ts`, `routes/explore.ts`; web `apps/frontend/src/routes/ExplorePage.tsx`, `lib/fisheye.ts`, `components/explore/`; apps `apps/mobile/lib/screens/explore_screen.dart`, `widgets/fisheye_wall.dart`, `widgets/explore_detail.dart`, `utils/fisheye_layout.dart`, `shaders/fisheye.frag`): all of TMDb, not just the library, for anyone who doesn't know what to watch, with where each title streams in India (TMDb's watch providers, which are JustWatch's data — the page credits both). Two views. The **wall** (default where WebGL2 works, unless the system asks for reduced motion) is up to 720 posters (360 on a phone) on one lattice seen through a fisheye lens, drawn by a single full-screen fragment shader — glossy raised frames lit by two moving lights, posters dimming and greying away from the middle; `GET /api/explore/wall` deals them out from several lists in turn so the middle is a mix. Drag (it coasts and settles on a poster), wheel/pinch zoom, click glides there and opens the panel; arrows/Enter/+/− on the keyboard. The **rows** view (`GET /api/explore`) is auto-drifting poster rows under a daily pick. Both share the filters (films/series, "In Campfire", up to three services — the backend accepts only the six listed in `EXPLORE_SERVICES`) and the details modal (`GET /api/explore/title/:type/:id`; 90% wide and centred on the web, the whole screen on a phone, with the trailer playing in its artwork): cast, where to stream/rent/buy, and "Play in Campfire" or a request/vote that goes through the normal request endpoints with the exact TMDb link. Every TMDb answer is cached in memory by its exact query (lists 6 h, titles 12 h) with at most 6 calls in flight, so the cost depends on how many *different* filter combinations get opened, not on viewers: a cold wall is about 50 calls, cold rows about 20. TMDb has no daily quota, only a burst limit around 40/s. Posters and logos load straight from TMDb's CDN, never through this server. `scripts/visual-home.mjs --explore` screenshots both views. The Android/Windows app has the same wall (its own tab, after Discover): the shader is ported to Flutter's dialect (`shaders/fisheye.frag`, registered under `flutter: shaders:`), which has no integer textures or texture arrays, so item numbers come from an RGBA index image and posters (96×144, 360 on a phone, 600 on desktop) are packed into one atlas image redrawn as they arrive; the middle poster gets a sharp w342 copy. The lens and layout maths live in `utils/fisheye_layout.dart` and must stay in step with `lib/fisheye.ts` and both shaders, or taps open the wrong poster. Without the shader the screen falls back to a plain poster grid; the app has no rows view.
- **Home's feed** (`lib/feed.ts`, `routes/feed.ts`; web `routes/HomePage.tsx`, `SectionPage.tsx`, `components/feed/`, `lib/feed.ts`): the web's Home is all of TMDb in about 40 sections (top ten, new and hot, cinemas, services, languages, genres, eras), six a page as the viewer scrolls, All / Films / Series, each openable at `/section/:id` as an endless grid. A page is made once a day by the first viewer to open it that day (India's date) and kept in Mongo (`feedPages`); a copy with a section missing isn't kept, and the last good copy stands in when TMDb isn't answering. `inLibrary` is added on every read. The client drops titles a section above already shows. Continue watching, For you and the library's own row sit among the sections; without `TMDB_API_KEY` Home is the library alone. Titles open in Explore's details modal (`?title=movie-603`, `useTitlePanel`), which has "More like this". Search covers the library, then TMDb. The old Discover grid is "Library" in the web's menu (same `/discover` route). `scripts/smoke-feed.mjs` checks it against a mock TMDb.
- **TMDb id is a title's identity** (`lib/tmdbRef.ts`): `tmdbRefOf` gives a film's, series' or episode's `{type, id, season?, episode?}` (null when unmatched, e.g. a home video), sent as `tmdb` on library cards and on `/api/folder` and `/api/video`. Anything belonging to a title rather than a file is keyed by it, so it survives the file being replaced. `GET /api/title/:type/:tmdbId[?season&episode]` finds a title in the library (web: `/title/movie/603`), `…/trailer` its official YouTube trailer (`lib/trailer.ts`, cached with Explore's TMDb answers). Admin's Catalog page lists titles without a match. Watch progress, parties and URLs still use the Drive file id.
- **Embedded players** (`lib/embed.ts`, `routes/admin/embeds.ts`; web `EmbedPlayer.tsx`, `admin/EmbedEditor.tsx`, `/admin/embeds`; apps `widgets/embed_player.dart`): an admin gives a title up to five players, tried in order before its Drive file, each with start-at / autoplay / muted / hide-controls where the provider has them. Only the providers in `PROVIDERS` (YouTube, Vimeo, Bunny, Cloudflare Stream, Internet Archive), checked on save and again on read — licensed hosts only; don't add URL templates that take a TMDb id, which is how unlicensed streaming sites work. `GET /api/video` leaves out ones their provider says are gone (cached; a viewer waits at most 2.5 s). On the web a player that reports an error (YouTube, Vimeo) or never loads moves on by itself, and buttons cover the rest; the apps open players in the browser. No party, resume or tracks: `?party=` always plays the file. `scripts/smoke-embeds.mjs` checks it against the real providers. Managed on the web admin only.
- **Video sources** (`lib/videoSources.ts`, `lib/videoHosts.ts`, `routes/admin/sources.ts`, `routes/sourceStream.ts`; web `/admin/sources`, `components/StreamPlayer.tsx`, `lib/useHls.ts`, `lib/players.ts`): the libraries titles play from — Bunny Stream libraries, Cloudflare Stream accounts, other sites' players, Drive — in one global order set in admin. A hosted source is the admin's own account: adding one takes its API key (sealed at rest with a key from `AUTH_JWT_SECRET`, never sent back), and only that service's own stream hosts are ever played. Its videos are listed every half hour and belong to a title by the TMDb id in their name (`keyFromName`: `tmdb-603`, `tmdb-1396-s1e2`). The rule: every title can be played from every source; no videos are selected or linked by hand, and the viewer picks the source. `GET /api/video` sends `players`: per-title embeds first, then the sources that have the title, Drive included; `GET /api/source-stream/:sourceId/:fileId` gives the 12-hour HLS address (signed for Bunny token authentication and Cloudflare signed URLs) or a 404, and the viewer is asked for another. On the web a stream plays in `VideoPlayer` (`streamUrl`, via hls.js, its own lazy chunk) with resume, up next, quality, captions, audio, speed and PiP; a source's `features` switch controls off one by one. A failure asks the viewer for another source, keeping the position. Parties always play Drive. The apps don't play sources yet. A third kind, **any player** (`lib/frameSource.ts`, kind `frame`), is added by pasting an iframe embed code with `{{file_id}}` in its `src` (the video's Drive file id, for a player holding the library's own files; no other placeholder is taken, and never a TMDb id): `parseFrameCode` reads the address, `allow`, `sandbox`, full screen, referrer policy, corners and shape, drops what reaches beyond the frame (top navigation, camera, event handlers, an address on Campfire's own host) and tells the admin what it left out. Every library video is tried in it, in its place in the order. The web plays it in `EmbedPlayer`, without resume or tracks. `scripts/smoke-sources.mjs` checks it against mocked APIs, the services' public demo streams and Bunny's signing test zone.
- **Watched, liked, disliked** (`lib/opinions.ts`, `lib/forYou.ts`, `routes/opinions.ts`; web `lib/opinions.ts`, `OpinionButtons.tsx`, `ForYouRails.tsx`): a viewer marks any TMDb film or whole series, in the library or not (Explore's panel, a series page, under a film's player; episodes and unmatched videos have no buttons). Kept in `titleOpinions` by TMDb id. A film played to its end counts as watched until the viewer says otherwise; marking a title watched takes it off Continue watching until it's played again. `GET /api/opinions` returns all of them at once and the clients look titles up in it. `GET /api/opinions/for-you` scores titles by their genres and lead actors (like 3, watched 1, started 0.5, dislike −3) plus TMDb's recommendations for up to six favourites, through Explore's cache: `library` (kind and id; the client has the cards) and `explore` (on TMDb, not in the library), each with a reason, nothing the viewer has seen, rated or started, and nothing that scores negative on taste. Up next leaves out watched and rated titles too. Not in the apps yet. `scripts/smoke-opinions.mjs` checks it against a mock TMDb.
- **Play on any title** (`lib/titlePlay.ts`, `routes/title.ts`, `routes/sources.ts`; web `lib/play.ts`, `routes/PlayPage.tsx`, `components/explore/SourceMenu.tsx`, `EpisodeList.tsx`, `components/SourcePanel.tsx`): every title on TMDb has a Play button, and it opens the list of sources (`GET /api/sources`: exactly the admin's enabled ones, in order, names only). Nothing is tried by itself: the viewer picks one, it's asked there and then (`streamFor` → `askHost`: the host's API searched by the TMDb number, 4 s, a miss kept 3 s), and if it hasn't got the title or can't play it the page says "Not found here" with the others to try. Don't add fallback from one source to the next. The next episode plays from the same source; with only one source it just plays. `GET /api/title/:type/:id/play` says where a title is watched: the library's own page, or `/watch/tmdb:movie:603` / `tmdb:tv:1396:s1e2` (`titleId`/`parseTitleId`), which `GET /api/video`, `/api/source-stream`, `/api/thumbnail` and progress all take as a video id (`titleVideo` gives it a library video's shape from TMDb); `?source=` names the one picked. `GET /api/video?all=1` (the web) has a player for every source; an app is only sent the ones known to have it. Any-player sources and Drive only have the library's own files. A title with only unpublished catalog videos is the admin's. A series carries on from the viewer's last episode; the details modal lists TMDb's seasons and episodes. Titles show in Continue watching for a client that asks (`/api/library?titles=1`). Not in the apps. `scripts/smoke-play.mjs` checks it with mock hosts and TMDb.
- **Windows player input** (`media_kit_video_player.dart`): mouse movement shows the controls (the cursor hides with them), a single click never pauses, a double-click on the left/right third skips 10 s per click and in the middle toggles full screen. The wheel and ↑/↓ set the volume, M mutes, F is full screen. The volume goes to 200% via mpv's `volume-max` (the boost zone drawn in amber) and is remembered.
- **Everything is plain HTTP, always** — no TLS anywhere in this repo (backend, frontend's `serve.mjs`, and every client). If you need HTTPS in production, put a reverse proxy in front and point each app's `*_URL`/`API_URL` config at that; nothing in the apps themselves needs to change either way.
- Deployment can also be pm2 on a single VPS over `http://<IP>:<PORT>` (no domain/reverse proxy) — root `ecosystem.config.js` reads the root `.env` (just ports; separate from each app's own `.env`) and starts both apps. See the root README's "Deployment" section.
- **CI and dependency updates** (`.github/workflows/ci.yml`, `.github/dependabot.yml`): every pull request and push to main runs backend type-check + lint (src *and* scripts), web build + lint, `npm audit --omit=dev --audit-level=high`, and `flutter analyze` + `flutter test` (on Linux — the tests are pure Dart). The smoke tests aren't in CI: they need MongoDB and the backend `.env`, so run them locally before a release. Dependabot opens weekly update PRs: ordinary minor/patch bumps grouped per ecosystem, majors one per PR, and media_kit / LiveKit / WebRTC (and googleapis / livekit-server-sdk on npm) always in their own PR, because CI can't play a video or hold a call — try those on a real device before merging. Keep `FLUTTER_VERSION` the same in `ci.yml` and `release-deploy.yml`.
